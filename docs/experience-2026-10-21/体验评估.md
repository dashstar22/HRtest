# 招聘筛选助手体验评估

体验日期：2026-10-21。依据面试官给出的四项功能要求，实际操作网页、调用真实 DeepSeek、执行现有自测，并用定向输入复核异常边界。未修改业务代码。

## 结论

四项核心要求均已具备可演示实现；人工标注、备注、重筛变化与导出形成了额外的业务闭环。可以作为面试 Demo。当前不能据此声称筛选准确率已得到验证，或证据检查可以杜绝虚构。

## 本轮验证

- 原 8000 服务已运行，已有一岗位四份简历。所有新增体验操作在 8001 服务的独立临时数据库执行，原演示库未改动。
- 网页从空态点击载入示例：真实 DeepSeek 完成 JD 解析与四份简历筛选，四份结果均为 `deepseek`，无规则降级。
- 首轮结果：张明远 88 / 李思颖 58 / 陈静 45 / 王浩 25；1 人建议复核、3 人暂缓。这是本轮样例结果，不是准确率评估。
- 查看张明远、陈静详情，检查符合条件、原文引用、待确认、优势、风险与简历原文入口。
- 采纳虚构样例张明远，保存备注“体验验证：确认 Python 项目职责后安排沟通。”；搜索“陈静”后只显示对应结果。
- 浏览器批量上传赵磊文本型 PDF 和扫描件样例：PDF 成功提取 484 字；扫描件被拒绝并给出“1/1 页只有图片、没有文字层”的建议；显示还有一份未筛选。
- 修改最低年限到 9 年：旧四份结果出现过期提示，人工采纳和备注保留。重筛五份成功，李思颖 58→52、陈静45→42；张明远仍为88，模型将其经验由8年重新推算为9年。不能仅据此认定它忽略修改。
- 将最低年限改为20年，定向重筛张明远：真实模型返回58分、hold、8年经验，明确指出20年要求不满足；原人工采纳和备注保留，页面显示下降30分及标注时88分。其余四人未在20年要求下重筛，仍正确显示过期。
- 实际点击导出 CSV，读回5行数据，确认备注存在；副本见 `export.csv`。
- 手动粘贴新 JD：“本科、3年以上Python后端、FastAPI或Django、MySQL，Redis加分”：自动解析出岗位名、部门、本科、3年、4个必备技能与1个加分项。OR关系被摊平成独立技能。
- 现有规则自测：47通过、0失败；本地mock AI自测：15通过、0失败。mock通过不代表真实模型质量已验证。

## 优先修复的问题

### 1. 引用前缀命中放过编造后半句

位置：`app/analyzer.py:136`。`verify_evidence`允许长引用仅前12个字符命中。

复现：原文为“负责Python后端开发与接口实现，未接触过Kubernetes。”，模型引用“负责Python后端开发与接口实现，并主导Kubernetes生产集群建设”，要求为“有Kubernetes生产经验”。校验后仍保留在matched中。

影响：当前不能声称所有展示引用都已完整定位。应校验完整归一化片段，或只展示实际定位到的原文；原文出现也不等于它逻辑上支持要求。

### 2. 结论归一化误判否定词；证据降级后分数与摘要未同步

位置：`app/analyzer.py:67`、`app/analyzer.py:123`。

定向输入`verdict=不推荐, score=20`被归一化成advance；`score=10, verdict=advance`也保留advance。原因是子串包含“推荐”就被判定推进，没有否定词或分数的一致性检查。

另一个定向输入为95分、advance、摘要“全部条件满足”，唯一证据完全不存在。证据被移至uncertain，但95分、advance和摘要全部保留。应对失效的关键证据触发重新评估或保守复核状态，并明确标注结论不一致；不能仅更新明细。

这些是合成模型输出的边界复现；本轮正常样例未出现“不推荐”的模型输出。

### 3. “或者”关系与年限依据缺少稳定表示

现有结构只有required_skills字符串列表。原JD和手工新JD中的“FastAPI或Django”均被拆成两个必备标签；原JD的“PostgreSQL / MySQL”也被拆开。陈静已有MySQL，详情仍额外追问PostgreSQL。AI仍能从全文识别部分OR关系，因此不能一概声称每次都按AND评分，但表示与判断存在不一致。

年限在同份简历不同轮次出现8、9、8年；“至今”的计算没有显式传入统一评估日期，自述年限与日期冲突时也没有固定优先口径。应保留原条件逻辑及推算依据，把冲突展示为待核实。

### 4. README 的隐私说明与实际数据流矛盾

位置：`README.md:308`、`app/prompts.py:43`。文档称“不发送文件名以外的候选人个人信息”，实际会发送完整简历文本，样例中包含姓名、电话、邮箱、性别、年龄等。当前未见调用前脱敏步骤，应如实说明发送内容；后续可考虑脱敏。

另有可直接核对的文档问题：

- “两种模式排序一致”不成立：规则下陈静70高于李思颖67，AI下李思颖58高于陈静45；建议人数相同不等于排序相同。
- API表写岗位更新“会清空旧结果”，实际为标记过期并保留人工决定。
- WAL与busy_timeout能缓解锁竞争，不能保证“并发写不再有锁风险”。
- README多处测试数仍为41/13/45，本轮实际为47/15。

## 次要体验问题

- 首次筛选没有上轮数据，仍显示“本轮结果与上次一致”；容易让面试官误解演示是否真正新跑。
- 上传第五份、尚未筛选时，上传区为5份，而结果统计卡“简历总数”为4。当前stats.total实际是结果数，应区分“上传总数/已筛选数”。
- 顶部“已连接deepseek-chat”只由配置Key推导，状态接口不发健康请求；应表述为已配置，真实调用成功状态另行展示。
- 模型失败原因虽在分析层生成，但未保存进结果表/API；详情只能看到“规则兜底”，难以解释具体为什么降级。

## 面试展示取舍

重点讲清楚：JD可调整、多个格式输入、语义区别于关键词、每条判断便于回查、人工决定保留、修改后过期与变化提示。无需为了本次Demo增加BOSS爬取、复杂Agent框架、向量库或多租户。

面试前优先处理证据检查、否定建议与结果一致性、README数据流说明；条件逻辑与年限口径紧随其后。不要将匹配分称为录用概率，不要把四份样例作为准确率结论。
